## 贡献前准备

在创建问题或提交改动前，请先完成以下检查：

- 阅读仓库根目录的 [README](../README.md)、相关目录的 README 及接口、配置和启动流程说明。
- 搜索已有 issue、讨论和提交，确认问题或建议尚未被报告，避免重复工作。
- 使用与目标一致的分支、配置和测试镜像复现问题；涉及行为变化时，先确认当前主线是否仍可复现。
- 将工作区中的临时文件、波形、日志、二进制镜像和构建缓存与待提交改动分开管理。

贡献可以使用中文或英文。为便于维护，请尽量准确、完整地描述背景、改动范围和验证结果。

## 报告问题与提出建议

### 缺陷报告

请将可复现的问题描述清楚，并尽可能提供以下信息：

- 使用的分支和 commit ID；
- 主机系统、关键工具版本和必要环境信息；
- 相关配置，例如 `CONFIG_MMU`、`CONFIG_SRAM`、开发板型号、软件镜像和启动参数；
- 预期行为、实际现象、完整或关键日志，以及最小复现步骤；
- 已尝试的排查方法，以及问题是否可稳定复现。

如果问题涉及 RTL 行为或差分测试失败，请尽可能附上最小测试程序或能够复现问题的镜像构建方式。提交日志、压缩包或配置文件前，请先检查其中不包含个人路径、凭据或其他敏感信息。

### 功能与流程建议

提出新特性、架构改进、性能优化或流程建议时，请说明使用场景、目标、对现有接口或兼容性的影响，以及可选实现方案。对于影响范围较大、接口变化明显或尚需讨论取舍的工作，建议先与维护者沟通，再投入实现。

尚未充分验证的实现、优化或架构探索应明确标记为“实验性”，并说明已知限制、适用条件和回退方式。

## 开发与提交

### 分支与改动范围

请为每项独立的功能、修复或实验性工作创建独立分支，名称应能反映用途，例如 `feature/cache-opt`、`fix/mmu-refill`、`docs/board-guide` 或 `experiment/perf-counter`。避免在主分支上进行长期开发。

每个提交和合并请求应聚焦一个主题，不要混入无关的格式调整、重命名或生成文件。必要的前置重构可以与功能改动一并提交，但建议拆分为独立、可审阅的 commit。

### 提交信息

提交信息应简洁说明“改了什么、为什么改、如何验证”。建议使用下列格式：

```text
type(scope): 简要说明

改动背景、实现方式与预期效果。

验证：执行的命令及结果。
```

常用的 `type` 包括：

- `feat`：新增功能；`fix`：功能或性能缺陷修复；`perf`：专项性能调优；
- `refactor`：不改变预期行为的重构；`test`：测试相关修改；`docs`：文档更新；
- `build`、`ci`、`chore`：构建、持续集成或日常维护；`style`：不影响功能的样式调整。

如有关联 issue，可在提交或合并请求描述中使用 `Fixes #编号` 关联；如有设计文档、讨论或第三方资料，可附上相应链接。

### 工程一致性

- 保持 RTL、仿真、FPGA 工程、软件测试和文档之间的接口一致。修改地址映射、配置参数、顶层端口或启动流程时，应同步更新相关脚本和说明。
- 新增测试应放入合适的 `verify/apps/` 或验证目录；新增脚本应有清晰用途、必要参数说明和合理默认值。
- 不要在脚本或工程文件中写死个人路径、工具链位置或本地环境变量。
- 遵循相关目录已有的代码风格、命名方式和文件组织；仅在确有必要时进行大范围格式化。

## 验证要求

提交前，请执行与改动范围相符的检查，并在合并请求中记录命令、配置和结果。可根据改动选择以下验证：

- RTL 编译或目标配置的构建；
- Verilator 仿真，包括必要的无差分和差分测试；
- 受影响的裸机应用、回归测试或最小复现程序；
- FPGA 工程构建，以及可用时的板级验证。

例如，Verilator 的默认构建和短冒烟测试可使用：

```bash
make -C verify/verilator
make -C verify/verilator test
```

对 Verilator、loong-emu difftest 或 FPGA 工程的修改，请明确列出 `CONFIG_MMU`、`CONFIG_SRAM`、板卡、镜像和其他影响结果的配置。若受工具、硬件或运行时间限制而无法完成某项验证，请明确指出未验证的项目及原因，而不要将其表述为已验证通过。

不要提交大型镜像、波形、日志、Vivado 临时目录、编译缓存或其他可再生构建产物，除非维护者已明确要求其用于问题定位。

## 合并请求与评审

提交合并请求前，请将分支整理为可独立构建、验证和审阅的状态。建议在描述中包含：

1. 改动动机和范围；
2. 实现要点，以及对接口、配置或兼容性的影响；
3. 验证环境、执行命令和结果；
4. 已知限制、未验证项和后续工作；
5. 关联的问题、讨论或参考资料。

请积极回应评审意见，并在更新后说明改动内容和重新执行的验证。评审的重点包括正确性、可维护性、验证充分性、文档完整性，以及与现有工程风格的一致性。维护者可能要求拆分过大的改动、补充测试或进一步说明设计取舍。

## 文档、许可证与第三方内容

修改文档时，请保证命令、路径、配置名称和描述与当前工程一致。中文和英文文档如同时维护，应避免相互矛盾；若暂时无法同步，请在提交说明中明确范围。

请尊重项目现有的版权声明和 [Mulan PSL v2](../LICENSE) 许可证要求。新增源码、脚本和文档应采用与工程一致的许可证文件头或声明。引入第三方代码、IP、工具或数据时，请明确其来源、许可证、版本及使用限制，并确认其与本项目的许可证兼容。

## AI 辅助使用

可以负责任地使用 AI 工具辅助翻译、润色、分析、编写代码或测试，但贡献者始终对提交内容负责。提交前请人工复核 AI 生成的代码、文档、测试和结论，确保其符合本说明并通过必要验证。

当 AI 参与生成了实质性代码、测试或完整问题描述时，建议在合并请求或 issue 中简要说明使用范围；如需在提交信息中标识，可使用 `Assisted-by: 工具或代理:模型版本`。不得将未审查的生成内容直接作为结论，也不得输入不应向外部服务披露的敏感信息。
